## 条款18：让接口容易被正确使用，不易被误用

**Make interfaces easy to use correctly and hard to use incorrectly.**

这个条款的核心是，作为类的设计者，我们设计接口时，应该使得用户在做正确的事情时感到自然、简单，在尝试做错误的事情时感到困难，甚至最好可以编译失败。

文章主要通过举例两个关键的示例，来阐述这个原则。例如在设计一个表示日期的 `Date` 类时：
```cpp
class Date {
public:
    // 一个设计上可能存在“误用”风险的接口
    Date(int month, int day, int year);
    ...
};
```

这个接口的问题：
- 参数顺序易错：用户很容易搞混 `month` 和 `day` 的顺序。
- 无效数值易入：用户可能传入无效的月份或天数。

为了解决这些问题，我们可以创建简单的 `struct` 或 `class` 来区分这三个整数的含义，并利用 C++ 的类型系统在编译期捕获错误。
```cpp
// 1. 定义独立的类型
struct Day {
    explicit Day(int d) : val(d) {}
    int val;
};

struct Month {
    explicit Month(int m) : val(m) {}
    int val;
};

struct Year {
    explicit Year(int y) : val(y) {}
    int val;
};

// 2. 在接口中使用这些新类型
class Date {
public:
    Date(const Month& m, const Day& d, const Year& y);
    ...
};
```

为了解决无效数值的问题，例如 13 月的问题，可以进一步强化 `Month` 类型，将将其构造函数设为 `private`，并提供静态成员函数来返回有效的月份。
```cpp
class Month {
public:
    static Month Jan() { return Month(1); } // 静态工厂函数
    static Month Feb() { return Month(2); }
    ...
    static Month Dec() { return Month(12); }
    // ... 其他成员函数 ...
private:
    explicit Month(int m); // 构造函数是私有的
    // ...
};

// 客户端使用
Date d(Month::Mar(), Day(30), Year(1995)); // OK！
```

通过这种设计，用户根本无法创建出一个代表 13 月的 `Month` 对象，从源头上杜绝了这种误用。

另一个示例是，假设有一个工厂函数，用于创建某种 `Investment` 对象：
```cpp
// 易被误用的接口
Investment* createInvestment();
```

这个接口的问题：
- 资源泄漏：用户必须记得在使用完毕后 `delete` 返回的指针。
- 所有权不明：不知道谁来负责释放这个指针，如果指针被多次传递，很容易导致忘记释放或重复释放。

改进的方法是返回一个智能指针（如 `std::shared_ptr`），将资源的所有权直接转交给一个资源管理类。
```cpp
std::shared_ptr<Investment> createInvestment()
{
    return std::shared_ptr<Investment>(new Stock());
}
```

通过这个设计，用户不再需要关心何时 `delete` 指针。`std::shared_ptr` 会在引用计数变为 0 时自动调用 `delete`。

文章还提到 `shared_ptr` 可以解决 cross-DLL problem。即在 Windows 上，如果一个对象在 `A.dll` 中 `new` 出来，但在 `B.dll` 中被 `delete`，而 `A` 和 `B` 链接了不同的 C 运行时库（CRT），这会导致堆（Heap）损坏和程序崩溃。

`shared_ptr` 的解决方案：`shared_ptr` 在其“控制块”中不仅存储引用计数，还会存储一个删除器。当创建 `shared_ptr` 时，它会记住创建它的那个 `DLL` 的 `delete` 操作。无论这个 `shared_ptr` 被传递到哪个 `DLL` 中，当引用计数归零时，它调用的都是最初那个 `DLL` 的 `delete`，从而完美避开了跨 DLL 内存释放的问题。

总结：可以把这个条款看成 C++ API设计的黄金准则，核心就是多利用 C++ 的类型系统和资源管理机制（如 `const`、`explicit`、智能指针、自定义类型等），让编译器来替用户把关，而不是依赖用户去记住复杂的使用规则。
